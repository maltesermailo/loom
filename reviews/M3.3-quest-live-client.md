## 2. What was built

- **`core::VideoReceiver`** — extracted the transport-agnostic receive pipeline (proto reassembly
  orchestration, §4.1 access-unit assembly, the §3.6 IDR policy, the freshness-capped decode
  hand-off) out of `sdl/video_pipeline.cpp` into `core/`, so both clients share it verbatim. The
  session prompt assumed this already lived in `core/`; it did not — a seam fix, done deliberately.
  SDL refactored onto it; SDL preset + latency test still green.
- **`quest/quic_transport`** — msquic-on-Android, a thin quest-local mirror of the SDL transport
  (the msquic C API is identical across platforms). `libmsquic.so` is built once by
  `scripts/build-msquic-android.sh` and linked as a prebuilt.
- **`quest/net_session`** — owns transport + `core::Session` + `core::VideoReceiver`; `pump()`
  drives the handshake, clock sync, IDR requests, and STATS on the OpenXR render thread (the SDL
  main loop, per the M3.3 threading decision).
- **`quest/hevc_decoder`** — repointed from the M3.2 looped file to the live receiver; capture_ts
  rides through as the codec pts and returns on the SurfaceTexture frame timestamp for the e2e
  overlay. Decode-loop hardened (§4).
- **`quest/overlay`** — the M1.3 fields on an OpenXR quad layer, refreshed every frame (so stats
  tick even when video freezes), CPU-rasterized with an embedded 5×7 bitmap font, toggled by the
  headset volume-up key (the Android input queue — no OpenXR action system, that is M4).

Batched decisions taken, all as recommended: render-thread pump; promote the receiver to `core`;
quest-local transport.

## 3. The protocol bug this surfaced (spec c7d8d38)

Loss testing (`--drop-percent`) exposed a **recovery deadlock in the shared, vector-tested receive
path** — pre-existing since M1, not M3.3-specific. §3.6 said the client SHOULD suppress further
IDR_REQUESTs "until a keyframe arrives"; on a lossy link a large IDR is itself lossy, so when the
recovery IDR was lost, the client suppressed forever, the host stopped sending IDRs, and the stream
froze for the rest of the session. Measured: recv froze at the first gap; host forced 12 IDRs in 3 s
then stopped while streaming continued 90 s; client IDR-request events frozen while gap-discards
climbed into the hundreds.

**Escalated rather than patched** (spec is read-only; this touches conformance vectors), then fixed
on your go-ahead as a proper protocol change: §3.6 keeps its only MUST (one request per 250 ms) but
**re-issues at that cadence** while the client still cannot decode. Landed across all three repos in
lockstep — spec prose + `generate.py` reference model + regenerated vectors (81 cases; four traces
unchanged, one renamed, one new), Rust host reassembler, C++ client reassembler + `VideoReceiver`.
vector-check green both impls; M1.2 recovery integration test still passes. **Proven on-device:** at
720p/1% loss recv now climbs continuously and host-forced IDRs climb past 50 — continuous recovery,
no deadlock.

## 4. Other bugs fixed

- **Missing `INTERNET` manifest permission** — a sandboxed app cannot open sockets without it; the
  M3.0 smoke test ran as shell and never hit this. This was why the first connect "succeeded"
  (ConnectionStart) but the host saw zero packets.
- **Decode-loop AU drop** — the loop popped an access unit and then dequeued an input buffer,
  silently dropping the AU (breaking the reference chain, no IDR) if none was free. Now reserves the
  buffer first.
- **Codec in-flight backlog** — bursty WiFi arrival let the decode thread stuff several frames into
  the codec (max-in-flight 5, decode tail 69 ms). A freshness cap holds it at ~2. Measured effect:
  in-flight 5→2, decode mean 19→15 ms, e2e ~117→82 ms, still 0 drops.

## 5. Measured (release loomd + VideoToolbox)

- Synthetic 1440p: ~68 fps, 0 drops, rtt ~13.8 ms, decode p50 ~15 ms, **e2e ~82 ms**.
- Real desktop (SCK): tiny P-frames, decode ~14 ms, **e2e ~60 ms**.
- Compositor: 72/72, 0 stale; overlay adds one quad layer (LCnt 2→3).

**e2e is over the ≤45 ms budget.** Pipeline accounts for ~30 ms; the remaining ~30–50 ms points at
WiFi latency (cf. the M3.1 `No hint: WIFI_LOW_LATENCY` warning, 6–95 ms ping jitter) and/or
clock-offset bias under WiFi downlink asymmetry — not resolvable by code. This is the carried M1.5
debt, not an M3.3 criterion; it needs the §12 physical (camera) measurement, which ROADMAP already
gates the latency pass on.
