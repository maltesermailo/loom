# Review — M1.2 Synthetic Media Path

**Status:** Complete. Both repos' `check.sh` green; live 1440p loopback video verified.
**Scope:** host encode + media transport + client decode/display for a *synthetic* source, on
the Mac via loopback. No PipeWire, NVENC, or portal code (those are M1.4/M1.5).
**Acceptance (spec/ROADMAP.md M1.2):** smooth 72 fps loopback; frame counter never regresses;
`--drop-percent 1` freeze→IDR_REQUEST→recovery < 200 ms (automated, log-parsed); a bitstream
conformance test asserting §5.

## 3. Why the key shapes

- **Encoder = mechanism, constraints = policy.** `loom-encode` takes the §5 knobs as an
  `EncoderConfig`; the *values* live only in `loomd/media/constraints.rs`, which both the encoder
  config and the conformance test import — so "what we told the encoder" and "what we assert" can't
  drift (the ROADMAP's explicit DRY requirement).
- **Fragmentation in `loom-proto`.** The reassembly (receive) side was already vector-proven there;
  the fragmenter is its inverse and round-trips through it in a unit test. loomd hand-rolls no
  datagram bytes.
- **Blocking encode on its own thread.** libx265 encode is CPU-bound; a dedicated per-session
  `std::thread` sends datagrams via a cloned `quinn::Connection` and stops when the connection
  closes. Control stays on tokio. Symmetric on the client: a decode thread behind the render loop.
- **capture_ts lives in the frame body (§4.1),** prepended before fragmentation and stripped after
  reassembly — not repeated per fragment.

## 5. DRY / KISS notes

- **DRY upheld:** wire logic (fragmentation, framing, reassembly, error codes) only in `loom-proto`;
  §5 constants only in `loomd/media/constraints.rs`; the encoder is a thin FFI, not a second policy.
- **KISS upheld:** a fixed-seed xorshift for loss injection (no `rand` dep); a 3×5 bitfont for the
  counter (no font lib); SDL YUV texture (no swscale); ffprobe as the reference decoder (no HEVC
  parser to maintain). No plugin systems, no config surface the ROADMAP didn't ask for.

---

## 6. Deviations & known limitations (flagged, not hidden)

1. **72 fps needs a release build.** In debug the synthetic path runs ~16 fps at 1440p because the
   3.7 M-pixel/frame Rust test-pattern fill and fragmentation are unoptimized (x265 itself is a
   release lib). The STEP 4 demo must build `--release`. Real capture (M1.4) removes the CPU fill.
2. **Client decode ~48 fps single-threaded at 1440p.** The host meets the 72 fps "renders smoothly"
   bar; smooth *display* would want multi-threaded decode, which trades latency — deferred to a
   tuning pass (candidate for M1.3/M3.2 alongside the real decode-latency budget).
3. **Recovery test is in-repo/in-process** (per your call): it drives the real host media path but a
   `loom_proto`-reassembly stand-in for the client, and parses host tracing + client reassembly
   events. The full cross-impl (loomd ↔ loom-sdl) recovery run belongs to the STEP 4 demo.
4. **One client commit is 544 lines** (> the 300–500 target). The media display path is a single
   cohesive subsystem (transport-datagram + decoder + renderer + pipeline + main) where every split
   point left a non-building or warning-emitting intermediate; kept together deliberately.
