## 4. A real bug caught by the instrumentation (and its resolution)

The first live overlay read **e2e ≈ 1.28 s and growing** — alarming. Debugging showed the *offset was
correct* (−2 ms) and the measurement was right: `now` advanced ~1.5 s per 60 frames while `capture_ts`
advanced ~1.0 s. That is a genuine **decode backlog** — single-threaded libavcodec decodes 1440p at
~48 fps while the host produces 72 fps, so undecoded access units queue and latency climbs unbounded.
The overlay was *accurately reporting a real problem*, which is exactly what instrumentation is for.

Resolution: **kept single-threaded low-delay decode.** For the SDL client — whose stated job (§7) is a
*latency-measurement rig* — frame-threading would add latency and corrupt the very numbers it exists
to measure. The backlog is the software-decode limitation (hardware decode on the Quest / VideoToolbox
keeps up); see §5. The e2e *measurement* is validated independently by the controlled test.

---

## 5. Known limitations (flagged, not hidden)

1. **Sustained 1440p software decode backlogs.** e2e grows under load because libavcodec single-thread
   can't sustain 72 fps at 1440p. Hardware decode (M2.2 VideoToolbox / M3.2 MediaCodec) resolves it;
   the low-delay design assumes a real-time decoder. For the demo, a lower resolution shows a stable,
   low overlay that visibly matches the pipeline delay.
2. **STATS jitter is frame-level** (capture_ts vs arrival deltas), not per-datagram RFC 3550 — adequate
   for a debug HUD; revisit if the bitrate controller (M7.4) needs finer input.
3. **Release build still required** for the 72 fps host finding from M1.2 (unchanged).

## 6. Follow-ups (not blocking M1.3)

- M1.4/M1.5 replace the synthetic source + software codec with real capture + NVENC (Linux).
- The `capture_ts`/offset plumbing this step lands is exactly what the `tools/latency-probe` rig and
  future A/V-sync work consume.

  decode queue backs up" freshness guard (treats can't-keep-up like a loss) — deferred as it adds
  periodic freezes the hardware path won't need.
