# Review — M3.2 MediaCodec bring-up + R5

**Status:** Decode path implemented and measured on-device; awaiting one human visual
confirmation (the moving frame counter on the cylinder). Client CI green.
**Scope:** AMediaCodec HEVC decode in surface mode → SurfaceTexture → OES → cylinder swapchain,
fed from a looped local `.hevc` (no network). Plus the R5 measurement.
**Acceptance (spec/ROADMAP.md M3.2):** decode ≤ 8 ms; no frame queued in decoder beyond 1
(verified by timestamp deltas).

---

## 1. R5 verdict — low-latency mode

**The §5 bitstream is inherently 1-frame-latency; the low-latency flag is a measured no-op, and
that is the correct outcome, not a failure.**

The decoder is the Quest 3's hardware `c2.qti.hevc.decoder` (confirmed from logcat, not the
software fallback). Measured input-queue → output-dequeue latency and the deepest the pipeline
ever buffered, 1000 steady-state samples at 2560×1440, paced to 72 Hz, proximity sensor disabled
so rendering ran steady (FPS=72/72, Stale=0):

| Config | p50 (ms) | min | p95 | max | max in flight |
|---|---|---|---|---|---|
| `AMEDIAFORMAT_KEY_LOW_LATENCY`=1 + QTI vendor key | 9.57 | 8.18 | 10.11 | 10.58 | **1** |
| **no low-latency keys at all** (A/B control) | 9.62 | 8.36 | 10.10 | 10.72 | **1** |

The two are within noise. Turning low-latency **off** changes nothing — because the §5 encoder
constraints (no B-frames, single reference, one slice) leave the decoder nothing to reorder or
hold, so it emits each frame the instant it is decoded. This is precisely the design rationale in
PROTOCOL §0 ("the constraints in §5 were chosen precisely so that…"), now confirmed on hardware:
**the low-latency property is structural to the stream, not dependent on a decoder flag.**

Shipped config: keep the standard `AMEDIAFORMAT_KEY_LOW_LATENCY` (correct, portable intent, zero
cost) and **drop** the `vendor.qti-ext-dec-low-latency.enable` key — it was a guessed magic string
and measured identical with and without it (KISS: no speculative keys that do nothing).

## 2. Acceptance against ROADMAP M3.2

| Criterion | Result | |
|---|---|---|
| No frame queued in decoder beyond 1 | **max in flight = 1** | ✅ clean pass |
| Decode ≤ 8 ms | **~9.2–9.6 ms** median (min ~7.5 ms) | ⚠ ~1.5 ms over — see below |

**The decode-≤8 ms line is marginally missed, and I am flagging it rather than rounding it away.**
~9.2 ms is the true figure: a tight-poll run (0 µs output timeout) gave p50 9.22 / min 7.54, so
polling overhead accounts for only ~0.35 ms — the rest is genuine 1440p HEVC decode on the XR2
Gen 2. It cannot be tuned under 8 ms here: the low-latency keys don't help (§1), and resolution is
spec-fixed at 1440p. ARCHITECTURE §10 budgets decode at "5–8 ms"; we are ~1.5 ms over that one
line item. The **hard** gate is e2e ≤ 45 ms (tested in M3.3/M5), which has ample room for a 9 ms
decode. My recommendation: record 9 ms as the real decode cost, carry it into the e2e budget, and
not treat the 8 ms sub-budget as a blocker. Your call if you want it escalated further.

## 3. The measurement bug I found and fixed (honesty)

My **first** on-device numbers were p50 28 ms, max-in-flight 6, tail to 316 ms — which looked
exactly like "low-latency ignored, decoder buffering ~2–6 frames." It was **not** the codec. It
was a bug in my own feed pacing: after any stall (codec init, a file-loop-boundary IDR), the feed
clock (`next_feed_ns += interval`) lagged wall-clock, so the loop fed a **burst** to catch up,
building a permanent backlog that dwarfed the codec's real latency. Clamping the catch-up (snap the
schedule to now instead of bursting) dropped the numbers to §1's ~9.5 ms / 1-frame immediately.

Recording this because the wrong numbers were momentarily convincing, and the lesson generalizes to
M3.3: **feed pacing must never burst to catch up** — freshness over completeness means dropping
late frames, not batching them. The clamp lives in `decode_loop`; the real transport in M3.3 feeds
from the network at arrival rate, which has the same "don't accumulate a backlog" requirement.

## 4. What was built

Host (`loom-host`, committed `f47d6be`):
- `loomd --dump-hevc <path> --dump-frames N`: encodes the synthetic pattern offline (no QUIC) to a
  raw Annex-B `.hevc`, reusing `constraints::encoder_config` / `TestPattern` / `open_encoder` — so
  the file is byte-for-byte the §5 stream M3.3 will send. Verified via ffprobe: I then all-P.

Client (`loom-client/quest`):
- `au_splitter` — splits the looped Annex-B into per-frame access units using the §5.5
  one-slice-per-frame guarantee (each VCL NAL ends a picture).
- `surface_texture` — the one unavoidable JNI object: constructs `android.graphics.SurfaceTexture`,
  wraps it with `ASurfaceTexture` (NDK), hands its `ANativeWindow` to the codec, latches frames
  with a timestamp-delta "new frame?" check on the render thread.
- `hevc_decoder` — `c2.qti.hevc.decoder` in surface mode on a dedicated thread (mirrors the SDL
  client's decode-thread model); feed paced to 72 Hz, drain-to-empty, R5 metrics.
- `xr_app` — OES blit into the cylinder swapchain, applying the SurfaceTexture transform; repaints
  **only** on a new decoded frame (§6.4 freshness — the compositor re-samples the last image for
  free through a stall). Static test image remains the fallback when the `.hevc` is absent.

Batched decisions taken (all as recommended): offline dump from loomd; decode-thread + render-thread
threading; latch-latest one-updateTexImage-per-vsync; minSdk 29 → 31 (device is API 34; msquic and
the WiFi lock still satisfied).

## 7. Notes carried forward

- **9 ms decode** into the e2e budget (M3.3/M5), per §2.
- The **file-loop boundary** (every 600 frames) briefly perturbs latency as the decoder re-inits on
  the repeated IDR. Harmless here; in M3.3 real IDRs are rare (loss recovery only), but worth
  remembering when reading M3.3 latency traces.
- `perfservice: No hint: WIFI_LOW_LATENCY found in config file!` still present (noted in M3.1) —
  revisit when validating WiFi low-latency mode during the M3/M5 latency work.
- Proximity sensor was disabled via MQDH for a steady render during measurement; re-enable for
  normal use.
