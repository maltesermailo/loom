# Review — M3.0 Spike R3: msquic on NDK

**Status:** Complete. **Verdict: msquic is viable on Android arm64. quiche is NOT required.**
Risk R3 (ARCHITECTURE §13) is resolved; the fallback stays shelved.
**Scope:** cross-compile msquic for Android arm64 from macOS, link a throwaway smoke-test binary,
prove a `loom/1` QUIC handshake with datagram support from the Quest 3 to `loomd --insecure-dev`.
No app code, no `client/` changes — the spike built entirely out-of-source and the repo is clean.
**Acceptance (spec/ROADMAP.md M3.0):** "QUIC handshake from on-device test binary to `loomd`." ✅

---

## 1. Verdict

msquic v2.5.9 (the pin the SDL client already uses) cross-compiles for `arm64-v8a` with the
NDK toolchain and completes a real handshake from the headset. Datagrams — the reason we chose
QUIC at all (PROTOCOL.md §0) — negotiate and are usable. **Recommendation: proceed with msquic
in M3.3, reusing the SDL client's `ExternalProject` pattern with the NDK arguments below.**

The one thing worth knowing up front: msquic does **not** list Android as an officially
supported platform (`docs/Platforms.md` covers Windows and Linux only; everything else is
explicitly "not to be considered officially supported"). That is not a blocker, and it is also
not a guess — Android is genuinely exercised:

- `.github/workflows/build.yml` builds `plat: android`, arm64, in CI on every change.
- The platform layer carries Android-specific handling: an `ANDROID_ABI` atomics workaround
  (`src/platform/CMakeLists.txt:40`), a skipped `pthread_setaffinity_np`
  (`src/platform/platform_posix.c:704`), an `IPV6_PKTINFO` note (`src/platform/datapath_epoll.c:769`).
- msquic treats Android as its `linux` platform (configure logs `QUIC Platform: linux`).

So: CI-tested, code-aware, unsupported-on-paper. Read that as "bugs may be looked at, not
guaranteed fixed", not as "untested".

## 2. What worked / what failed

| Step | Outcome |
|---|---|
| NDK toolchain on Apple Silicon | ✅ native — see §3 |
| cmake configure (`android.toolchain.cmake`, arm64-v8a, android-29) | ✅ first try |
| quictls (OpenSSL) configure | ❌ **failed once** — the one real friction point, below |
| msquic build → `libmsquic.so` | ✅ after the fix |
| smoke-test cross-compile + link | ✅ first try |
| on-device handshake to `loomd` | ✅ |

**The one failure.** OpenSSL's `Configure` reads the NDK path from the *environment*, not from
cmake: `Configurations/15-android.conf:27-32` checks `$ENV{ANDROID_NDK_ROOT}` / `$ENV{ANDROID_NDK}`
and dies otherwise. Passing `-DANDROID_NDK=` at configure time is not enough — the variable must
be exported in the shell that runs the *build*, because that is when quictls configures itself.
Symptom is a one-liner buried in an otherwise healthy log:

```
$ANDROID_NDK_ROOT is not defined at (eval 10) line 32.
Failure!  build file wasn't produced.
```

Fix: `export ANDROID_NDK_ROOT=$NDK` for the build step too. Worth encoding in the CMake wiring
rather than a README instruction, since a stale environment reproduces this exactly.

⚠ **The NDK on this machine is a beta.** Everything here passed on it, but shipping M3 on
`r30-beta1` is a choice, not a default — flagged as a decision for M3.1, not resolved here.

⚠ **adb was over USB, not wireless.** `adb mdns services` listed nothing. The handshake itself
still crossed real WiFi (QUIC is UDP; `adb reverse` cannot tunnel it), so the network result is
honest — but the wireless-adb deploy loop the session assumes is unproven.

## 4. Build recipe (reproducible)

```sh
NDK=$HOME/Library/Android/sdk/ndk/30.0.14904198
export ANDROID_NDK_ROOT=$NDK          # REQUIRED at BUILD time — see §2

cmake -S <msquic-src> -B <build> -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=$NDK/build/cmake/android.toolchain.cmake \
  -DANDROID_ABI=arm64-v8a \
  -DANDROID_PLATFORM=android-29 \
  -DANDROID_NDK=$NDK \
  -DCMAKE_BUILD_TYPE=Release \
  -DQUIC_TLS_LIB=quictls \
  -DQUIC_BUILD_TOOLS=OFF -DQUIC_BUILD_TEST=OFF -DQUIC_BUILD_PERF=OFF \
  -DQUIC_ENABLE_LOGGING=OFF
cmake --build <build> -j
```

Arguments match msquic's own CI (`scripts/build.ps1:516-534`), which is why they work.
`ANDROID_PLATFORM=android-29` is theirs; Quest 3 runs well above it.

## 5. Artifacts

| Artifact | Value |
|---|---|
| `libmsquic.so` | ELF aarch64 shared object, **6.2 MB** unstripped (with debug_info) / **3.3 MB** stripped |
| `DT_NEEDED` | `libdl.so`, `libm.so`, `libc.so` — **nothing else**: no OpenSSL runtime dependency, no libc++ |
| smoke binary | 9.3 KB; needs `libmsquic.so` + `libc++_shared.so` (the latter from the test's own C++ use) |

The dependency list is the good news for packaging: quictls is inside the `.so`, so the APK
ships one library and no crypto runtime.

## 6. Datagram API availability

Available and negotiated. The client advertises `QUIC_SETTINGS.DatagramReceiveEnabled = TRUE`
(`msquic.h:811`); the peer's support arrives as `QUIC_CONNECTION_EVENT_DATAGRAM_STATE_CHANGED`
with `SendEnabled` / `MaxSendLength` (`msquic.h:1341-1344`, verified against the header on disk).
Note `MsQuicOpenVersion` is the library's only exported symbol — the datagram API lives in the
`QUIC_API_TABLE` function table, not in separate exports, so `nm` on the `.so` is not the way to
check this. The runtime event is.

On-device run against `loomd --insecure-dev` at `192.168.178.72:47800`:

```
[smoke] CONNECTED — loom/1 handshake complete
[smoke] DATAGRAM_STATE_CHANGED SendEnabled=1 MaxSendLength=1188
[smoke] DATAGRAM_STATE_CHANGED SendEnabled=1 MaxSendLength=1220
[smoke] DATAGRAM_STATE_CHANGED SendEnabled=1 MaxSendLength=1300
[smoke] DATAGRAM_STATE_CHANGED SendEnabled=1 MaxSendLength=1380
[smoke] DATAGRAM_STATE_CHANGED SendEnabled=1 MaxSendLength=1440
[smoke] settled MaxSendLength=1440 after 20s
[smoke] VERDICT: handshake=OK datagrams=OK max_send=1440
```

## 7. Finding to carry into M3.3 — the PMTUD startup window

`MaxSendLength` **starts at 1188 and climbs to 1440 over roughly the first seconds** of the
connection, as QUIC path-MTU discovery probes upward from its conservative 1280-byte baseline.

The host fragments to a **full 1350-byte datagram** (`host/loom-proto/src/datagram.rs:22,96` —
`MAX_DATAGRAM_LEN = 1350`, `MAX_PAYLOAD = 1338`), which PROTOCOL.md §2 permits as its ceiling.
1440 > 1350, so **the steady state is fine and the spec's ceiling is reachable on this path**.
But for a window at session start the usable datagram size is *below* 1350.

Two honest caveats on how far this observation reaches:

1. It measures **client→host** (msquic's send limit). Media flows **host→client**, governed by
   quinn's own PMTUD. Same physics, not the same measurement — I did not measure quinn's side.
2. Whether quinn actually refuses or drops an oversized `send_datagram` during that window is
   **unverified**. I did not run media through it; that is M3.3's job.

If it does bite, the symptom is benign and self-healing by design: early frames drop, the client
freezes on nothing, and §3.6's IDR_REQUEST recovers — the loss path M1.2 already proves. Worth
watching in M3.3 rather than pre-solving. **Not a spec problem:** §2 sets 1350 as a maximum, so a
host fragmenting smaller stays conformant.

## 8. Minor caveat for M7

quictls configured with `--openssldir="/opt/homebrew/etc/openssl@3"` — a *macOS host* path baked
into an *Android* library, inherited from the build machine. Harmless now (we use
`QUIC_CREDENTIAL_TYPE_NONE` + `NO_CERTIFICATE_VALIDATION` under `--insecure-dev`, and M7 pins
certs explicitly rather than consulting a CA directory), but it would matter to anything that
falls back to the default CA store. Noted so it is not rediscovered in M7.

## 9. Spike disposition

The smoke test is throwaway and lives in the session scratchpad, not the repo — its job was the
verdict above. The build recipe (§4) is the part worth keeping; it lands in `quest/`'s CMake
wiring in M3.1/M3.3, with `ANDROID_NDK_ROOT` exported by the build system rather than documented.

`client/check.sh` green; no `client/` files changed by this spike.
